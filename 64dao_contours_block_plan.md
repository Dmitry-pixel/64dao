# План реализации: мультиконтурная диагностика (продукт · рынок · процессы)

Исполнитель: Claude в репозитории `Dmitry-pixel/64dao`.
Основа: реализованный финансовый блок (`finance_hexagram_questionnare_spec.MD`, `64dao_metod1_finance_block_plan.MD`, миграция 007, модули `finance_*`). Новые контуры строятся обобщением этой механики, не копированием.

---

## 0. Зафиксированные решения

1. **Механика контура = механика финансового блока**: 6 блоков × 4 утверждения, шкала 1–4 + «не знаю», реверсивные пункты, вето на пункте 4.1 (линия 4), подвижные линии (≥3.5 / ≤1.5), результирующая гексаграмма = инверсия подвижных линий. Карта `_TARGET_HEXAGRAM` к контурам не применяется.
2. **Единая семантика 6 линий** для всех контуров: процессы → системы → команда → поддержка руководства → внешняя среда → стратегия. Следствие: предикаты R1–R12, квадранты, триграммы, тональности и вето-логика переиспользуются без изменений. Контурная специфика — только в формулировках 24 утверждений.
3. **Флоу — инкрементный**: база (6 вопросов) + финансовый блок остаются обязательной анкетой Метода 1 как сейчас (30 шагов). Контуры продукт/рынок/процессы пользователь проходит из кабинета в любой момент после завершения диагностики; отчёт дополняется секциями при регенерации.
4. **Монетизация не меняется**: один кредит = одна диагностика со всеми контурами. Прохождение дополнительного контура кредит не списывает.
5. **Контент — fallback без LLM (v1)**: слои A–E из `fin_content` становятся общей базой; контурное переопределение поддерживается схемой сразу, наполняется постепенно через админку. AI-адаптация текстов — v2, отдельный релиз.
6. **Слой E (пакеты действий)** — общий на старте, контурные переопределения потом.
7. **Хранение — новая таблица `assessment_contours`**, финансовые данные мигрируются в неё. Клонирование колонок `finance_*` ×3 запрещено (дубли доменной логики).
8. **Повторное прохождение контура в v1 не поддерживается** (перезапись запрещена). Повторная диагностика и динамика — отдельный пункт роадмапа (3.1), не смешивать.

## 1. БД — миграция 009

### 1.1 Новая таблица `assessment_contours`

```
id            UUID PK
assessment_id UUID FK assessments.id ON DELETE CASCADE, NOT NULL, index
contour       String(20) NOT NULL  — CHECK IN ('finance','product','market','process')
answers       JSONB NOT NULL       — {"1.1": 3, "1.2": null, ...}
result        JSONB NOT NULL       — снимок скоринга (структура = текущий finance_result)
combination   String(6) NOT NULL   — CHECK ~ '^[AB]{6}$'
created_at / updated_at
UNIQUE(assessment_id, contour)
```

Статус-поле не нужно: запись создаётся только по факту успешного скоринга (completed по определению). Черновик контура при необходимости живёт в состоянии фронта.

### 1.2 Миграция данных

`INSERT INTO assessment_contours SELECT ... FROM assessments WHERE finance_result IS NOT NULL` (contour='finance'). Колонки `assessments.finance_*` **не удалять** в 009 — оставить как rollback-окно; код после этапа 2 читает только новую таблицу. Удаление колонок — отдельная миграция 010 после стабилизации (зафиксировать follow-up).

Черновики (`finance_answers` без `finance_result`) остаются в старых колонках до дозаполнения через существующий флоу — они завершатся в новую таблицу через обновлённый сабмит.

### 1.3 `fin_content`: контурное переопределение

```
+ contour String(20) NULL  — NULL = общий базовый контент; CHECK IN (...) OR NULL
UNIQUE(kind, key) → UNIQUE(kind, key, contour)
```

Резолюция контента: запись (kind, key, contour) → если нет, (kind, key, NULL). Таблицу не переименовывать (KISS); зафиксировать в docstring, что имя историческое, содержимое — общая библиотека интерпретации контуров.

## 2. Backend

### 2.1 `app/contours.py` — реестр контуров

```
CONTOURS = {
  'finance': {title, intro_text_key, items: FINANCE_ITEMS},
  'product': {...}, 'market': {...}, 'process': {...},
}
```

- Структура item та же: `{item_id, block, block_title, line_key, text, reverse, veto}`.
- Инварианты (проверять тестом для каждого контура): 24 пункта, 6 блоков × 4, ровно один reverse на блок, вето только на 4.1, line_key из единого набора (processes/systems/team/leadership/environment/strategy).
- `finance_items.py` становится источником items контура finance; тексты остальных контуров — по тому же образцу (это скоринг-конфиг, живёт в коде, не в БД — по аналогии с решением §0.5 финансового плана).
- До получения утверждений от владельца новые контуры регистрируются с `enabled: false` (per-contour feature flag в `config.py`) — код деплоится, контур не виден пользователю.

### 2.2 Обобщение скоринга и интерпретации

- `finance_scoring.compute_finance_result` → `contour_scoring.compute_contour_result(answers, items)`. Логика не меняется (она уже не зависит от предметки). Контрольный кейс Спецификации §3.7 обязан проходить без изменений.
- `finance_interpret`: предикаты без изменений; `load_content(session)` → `load_content(session, contour)` с fallback-резолюцией §1.3.
- `finance_service` → `contour_service`: текущая функция `resolve_submission_finance` остаётся для сабмита Метода 1 (контур finance), плюс новая `submit_contour(assessment, contour, answers)` для инкрементных контуров.
- Старые модули оставить как тонкие реэкспорты или удалить с правкой импортов — единый источник логики, без двух копий.

### 2.3 API

- `GET /api/method1/contour-items/{contour}` — пункты анкеты контура (формат текущего `finance-items`). Существующий `GET /api/method1/finance-items` оставить как alias (фронт мигрирует, потом удалить — follow-up).
- `POST /api/assessments/{id}/contours/{contour}`:
  - авторизация: владелец диагностики;
  - диагностика в статусе completed/paid; контур enabled; записи ещё нет (409 при повторе);
  - тело: `{answers}`; скоринг только на сервере; ответ: результат контура;
  - после записи — инвалидация/регенерация отчёта (по текущему механизму generate-report).
- `GET /api/assessments/{id}` — дополнить списком пройденных контуров (contour, combination_current, combination_resulting, created_at).
- `GET/PUT /api/fin-content` — поддержка поля contour (фильтр + запись переопределений), admin-only на запись.

### 2.4 Отчёт и PDF

- `_finance_section_html` → `_contour_section_html(contour, result, content)`; структура 9 подразделов не меняется. Заголовок секции — название контура.
- Порядок секций отчёта: базовые (ЖЦ, переход, стратагема) → сводная карта контуров → секции контуров (finance, product, market, process — только пройденные).
- **Сводная карта контуров** (новый раздел, выводится при ≥2 пройденных контурах):
  - таблица: контур | текущая гексаграмма (SVG, номер, название) | результирующая | maturity_index | число подвижных линий;
  - выделение контура с минимальным maturity_index как кандидата в системное ограничение (формулировка: «наиболее вероятная зона системного ограничения по данным диагностики»);
  - расхождение ≥3 по maturity_index между контурами — отдельный акцент.
- Legacy-диагностики (только finance или вообще без контуров) регенерируются без ошибок: нет контуров → нет сводной карты, нет секций.
- `page-break-inside: avoid` на карточках, по образцу существующих блоков.

## 3. Frontend

1. Вынести финансовый степпер из `assessment/page.tsx` в компонент `ContourSurvey` (props: contour, items, onSubmit). Флоу Метода 1 использует его для finance — поведение анкеты не меняется.
2. Дашборд, карточка завершённой диагностики: блок «Контуры диагностики» — finance с бейджем «пройден», product/market/process — кнопка «Пройти» (только enabled-контуры). После прохождения — мини-гексаграммы (текущая/целевая).
3. Страница `assessment/contour/[contour]` (или модальный флоу с дашборда): интерстициальный экран (название, 24 утверждения, ~10 минут) → `ContourSurvey` → сабмит → возврат к отчёту с новым разделом. Предупреждение о потере данных при уходе.
4. Страница отчёта: секции контуров + сводная карта (зеркально PDF).
5. Админка: в редакторе fin_content — селектор контура (общий / переопределение); индикация, какие ключи переопределены.
6. `lib/api.ts`: типы контуров.

## 4. Тесты

1. Обобщённый скоринг: контрольный кейс §3.7 проходит на `compute_contour_result` c items финансов (байт-в-байт прежний результат).
2. Инварианты реестра: для каждого контура — 24 пункта, структура блоков, один reverse на блок, вето 4.1.
3. Миграция 009: fixture с finance-данными → перенос в `assessment_contours` без потерь; результат отчёта до/после идентичен.
4. API контуров: 401/403 чужая диагностика; 409 повторный сабмит; 400 невалидные ответы; 404/403 disabled-контур; успешный сабмит пишет result и combination.
5. PDF/HTML: отчёт с 1, 2 и 4 контурами; сводная карта появляется с ≥2; legacy без контуров.
6. Fallback контента: контурная запись перекрывает общую; отсутствие обеих → «Не заполнено».
7. Регресс Метода 1: анкета 6+24, кредиты, generate-report — без изменений поведения.

## 5. Порядок работ (этапы = отдельные PR)

1. **Миграция 009 + модель + перенос finance-данных + переключение чтения** на `assessment_contours`. Самый рискованный этап: полный регресс финансового флоу, деплой отдельно.
2. Обобщение `contour_scoring` / `contour_service` / `interpret` + реестр с одним контуром finance + юнит-тесты (без UI).
3. Реестр 3 новых контуров (тексты-заглушки, `enabled=false`) + API endpoints + тесты.
4. Фронт: `ContourSurvey`, дашборд, страница прохождения контура.
5. Отчёт: `_contour_section_html`, сводная карта, PDF + тесты.
6. Контент: 24×3 утверждения от владельца → в реестр; вводные тексты; поконтурное включение флагов (запуск каждого контура по готовности его утверждений).
7. Админка контурных переопределений контента + `fin_content.contour` в CRUD.

Этапы 1–5 не зависят от контента и идут параллельно с его подготовкой. Критический путь запуска — утверждения (этап 6).

## 6. Контент с владельца (критический путь)

- 24 утверждения × 3 контура в структуре финансового опросника: 6 блоков единой семантики линий, в каждом ровно один реверсивный пункт, пункт 4.1 — вето (приверженность первого лица приоритету данной функции).
- Вводный текст на контур (интерстициальный экран + вводка секции отчёта) — 4 шт., включая финансовый (для единообразия).
- Особое внимание — контур «рынок»: линия 5 (внешняя среда) семантически близка предмету контура; формулировки должны разводить «зрелость рыночной функции компании» (линии 1–4, 6) и «турбулентность самого рынка» (линия 5).
- Контур «процессы»: линия 1 (процессы функции) внутри контура операционных процессов — трактовать как «документированность и устойчивость ключевых операционных процессов»; не дублировать формулировки финансового блока.

## 7. Риски

| Риск | Уровень | Митигация |
|---|---|---|
| Миграция finance-данных в новую таблицу | Высокий | Колонки не удалять (rollback-окно), сверка счётчиков до/после, отдельный PR, регресс отчётов |
| Формулировки «рынка» в единой рамке линий | Средний | Ревью формулировок до включения флага; флаг per-contour позволяет запускать контуры независимо |
| Вёрстка сводной карты в PDF | Средний | Фикстурный рендер 4-контурного отчёта на этапе 5 |
| Рост объёма отчёта (4 контура × 9 подразделов) | Низкий | Инкрементный флоу: у большинства пользователей 1–2 контура |
