# Спецификация и план: чек-лист перехода с прогрессом (роадмап 3.2)

Исполнитель: Claude в репозитории `Dmitry-pixel/64dao`.
Зависимости: маршрут перехода (2.1, `contour_route.py`) — источник шагов; компании и подписка (3.1) — доступ и привязка. Реализуется после обоих.

---

## 0. Зафиксированные решения (выведены из 2.1 и 3.1)

1. **Чек-лист = проекция маршрута перехода в задачи.** Шаг маршрута (смена одной подвижной линии контура) → задача чек-листа; пункты пакета действий шага (слой E) → подзадачи-ориентиры внутри задачи.
2. **Доступ — при активной подписке** (тарифная конструкция 3.1: чек-листы входят в мониторинг-подписку). Без подписки — превью с замком и CTA.
3. **Прогресс привязан к конкретной диагностике** (маршрут детерминирован её снимком `result`). Повторная диагностика создаёт новый чек-лист; старый архивируется с сохранением отметок.
4. **Сверка диагностикой**: при повторном прогоне система сравнивает линии — если подвижная линия из старого снимка изменилась в целевую сторону, соответствующая задача получает отметку «подтверждено диагностикой». Ручная отметка пользователя и объективная сверка — два независимых признака.
5. Пользователь может добавлять **свои задачи** (текстовые) к любому контуру — важно для консультантов, ведущих клиента.

## 1. Данные — миграция (следующий номер)

```
checklist_items:
  id            UUID PK
  assessment_id UUID FK CASCADE, index
  contour       String(20) NULL      — NULL для задач сводного маршрута/custom без контура
  kind          String(10)           — 'step' | 'custom'
  step_order    Int NULL             — для kind='step': порядок в маршруте
  line          Int NULL             — для kind='step': номер линии
  title         Text                 — заголовок (для step — генерируется из маршрута)
  status        String(12)           — 'todo' | 'done'
  note          Text NULL            — заметка пользователя
  done_at       timestamptz NULL
  verified_by   UUID NULL FK assessments.id  — диагностика, подтвердившая шаг (§4)
  created_at / updated_at
  UNIQUE(assessment_id, contour, step_order) WHERE kind='step'
```

Генерация: лениво при первом открытии чек-листа диагностики — из `build_route()` по снимку; идемпотентно (существующие items не пересоздаются). Подзадачи-ориентиры (пункты пакета действий) не хранятся отдельно — рендерятся из контента по `action_key` шага; отметка ставится на уровне задачи-шага (KISS: не плодить сущности ради галочек на подпунктах).

## 2. API

- `GET  /api/assessments/{id}/checklist` — задачи + прогресс (генерация при первом вызове). Доступ: владелец + активная подписка (единый helper `subscription_service.is_active`, без дублей проверок).
- `PATCH /api/checklist/{item_id}` — status, note (только владелец).
- `POST /api/assessments/{id}/checklist` — custom-задача {title, contour?}.
- `DELETE /api/checklist/{item_id}` — только kind='custom'.
- Прогресс компании (для карточки и динамики): считается на лету из items последней диагностики.

## 3. Frontend

- Вкладка «План перехода» на странице отчёта / карточке компании: группировка по контурам (порядок сводного маршрута — контур-ограничение первым), задачи с чекбоксами, раскрывающиеся ориентиры из пакета действий, заметки, добавление своих задач, общий прогресс-бар.
- Бейджи: «подтверждено диагностикой» (✔ из сверки) отдельно от ручной отметки.
- Без подписки: превью структуры (контуры + число шагов) с замком.
- Архив: на старых диагностиках чек-лист read-only с пометкой «архив».

## 4. Сверка при повторной диагностике

При создании нового completed-прогона той же компании:

```
для каждого step-item последнего чек-листа предыдущей диагностики:
    линия L контура C была подвижной со state S (old_yin | old_yang)
    новый снимок: символ линии L контура C
    если символ изменился в целевую сторону (old_yin: B→A; old_yang: A→стабильный A
    без подвижности или управляемое снижение) → verified_by = новый assessment_id
```

Точное правило для old_yang (риск перегрева «снят», если линия перестала быть подвижной) — зафиксировать в коде с тестом; методологическая формулировка согласована: цель шага old_yang — стабилизация, а не инверсия.

Результат сверки показывается в чек-листе и в разделе «Динамика» (3.1, секция «Сводка»): «выполнено и подтверждено / отмечено, но не подтверждено / подтверждено без отметки».

## 5. Тесты

1. Генерация из маршрута: число задач = число шагов, порядок, идемпотентность повторного вызова.
2. Доступ: 403 без подписки; чужая диагностика; custom-задачи — CRUD, step-задачи не удаляются.
3. Сверка: old_yin B→A → verified; линия не изменилась → нет; old_yang перестал быть подвижным → verified; регресс línии — нет.
4. Архивация: старый чек-лист read-only, новый генерируется от нового снимка.
5. Контур без подвижных линий → пустой раздел «стабилен», без задач.

## 7. Риски

| Риск | Уровень | Митигация |
|---|---|---|
| Правило сверки old_yang неочевидно пользователю | Средний | Пояснение в UI у бейджа; формулировка «риск снят» вместо «выполнено» |
| Пользователь ждёт галочек на подпунктах действий | Низкий | v1 — отметка на уровне шага; если запросы будут, добавить granular-отметки отдельной таблицей |
| Чек-лист без подписки воспринимается как урезанный отчёт | Низкий | Превью честно показывает структуру; сам маршрут (2.1) остаётся в отчёте без подписки — платен только трекинг |
