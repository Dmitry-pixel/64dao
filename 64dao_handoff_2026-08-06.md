## 2. Как здесь принято работать

Правила заданы владельцем. Они не обсуждаются по ходу — их соблюдают.

**Команды в консоль, шаг за шагом.** Вы присылаете блок для вставки, получаете
вывод, оцениваете, присылаете следующий. Локальный компьютер не используется.

**Перенос файлов — через base64.** Файл в `tar.xz` или `xz`, base64 кусками
по 96 строк, после каждого куска `md5sum`, после сборки — `md5sum` итога.
Куски по 195 строк портились дважды, по 96 проходят надёжно.

**Патчи вместо якорных скриптов.** Изменения удобнее доставлять как
`git diff` и применять `git apply`. Обязательно сначала `git apply --check`:
он показывает, ляжет ли патч, ничего не меняя. Патч до ~150 строк вставляется
текстом напрямую, больше — через base64. За эту сессию так доставлено пять
изменений, все легли чисто.

**Опасное действие — отдельным блоком от диагностики.** Ошибка этой сессии:
проверка содержимого таблицы и `DROP TABLE` стояли в одном блоке, а в тексте
было написано «если проверка покажет X — остановиться». Остановиться было
невозможно: всё выполнялось разом. Разделяйте.

**Пересборка фронтенда — только `--no-cache`** и с `--build-arg
NEXT_PUBLIC_API_URL=https://64dao.ru`. Обычная сборка берёт слой из кэша,
и в бандл попадает старый код.

**Планы до кода.** Владелец просил: сначала план, потом реализация.

**Кавычки в `docker compose exec db sh -lc "psql -c ..."` не выживают.**
Двойное экранирование через два слоя оболочки рвёт SQL. Передавайте SQL
через stdin: `docker compose exec -T db sh -lc 'psql -U "$POSTGRES_USER"
-d "$POSTGRES_DB"' <<'SQL' ... SQL`.

## 3. Что нельзя ломать

### Деньги и доступ

**Балансы продуктов раздельные.** `m12` — Методы 1 и 2 (один заказ покрывает
оба и повтор Метода 1), `m3` — Метод 3 (один портфель за заказ). Цены разные,
поэтому общий кошелёк даёт арбитраж: кредит куплен дешевле, потрачен на
дорогое. Это же правило действует для грантов: у гранта есть продукт, гранта
«на всё» нет намеренно.

**Заказ — покупка кредита на продукт, а не оплата конкретной диагностики.**
`orders.assessment_id` больше не `NOT NULL`; привязка проставляется в момент
списания. Без этого нельзя было ни продать Метод 3, ни купить диагностику
заранее.

**Обратной ссылки `orders → m3_portfolios` нет и быть не должно.** Вместе с
`m3_portfolios.order_id` она образует цикл внешних ключей, на котором
SQLAlchemy не сортирует таблицы: `create_all` и `drop_all` падают
с `CircularDependencyError`, и весь набор тестов ложится каскадом.

**Списание Метода 3 стоит на `calculate`.** Единица расхода — рассчитанный
портфель: до расчёта пользователь не получил ничего, что стоит денег. Порядок
внутри эндпоинта важен: сначала выбор источника оплаты (403 при пустом
балансе), потом расчёт, и только на успешном расчёте — отметка списания.
Иначе неудачная валидация анкеты съедает кредит.

**Администратор проходит бесплатно** — во всех контурах, решение владельца.

### Отчёты и карта

**Ключи долей выручки в карте портфеля приводятся к строке.** Веб отдаёт их
из JSON строками, сборщик PDF — из ORM, где `object_id` остаётся `uuid.UUID`.
Разнотипные ключи молча не находят долю, и все круги рисуются минимальным
радиусом. Это уже случилось: картинки веба и PDF расходились.

**`updated_at` не добавлять в `M3PortfolioOut`.** У колонки `onupdate=func.now()`,
после flush SQLAlchemy помечает её протухшей, и сериализация ответа лезет за
значением вне async-контекста: `MissingGreenlet`, 500 на `PUT owner-ranks`.

**Заголовок веб-отчёта Метода 1 совпадает с PDF.** В `h1` — «Стратегический
профиль компании», название стратегии — подзаголовком. Раньше в `h1` попадал
`strategy.title`, и заголовок не выводился никогда.

**Правило одно, отчётов два.** Вердикты, траектория, причина места в очереди
и разбор раздела 03 считаются в `m3_service.build_report`; `m3_pdf` вызывает
те же чистые функции на том же словаре. Охраняется `test_m3_report_parity.py`.

**Третьей копии правил карты в TypeScript быть не должно.** Две копии
(React и Python) синхронизируются вручную — это потолок. Эталон:
`node backend/tests/fixtures/gen_m3_map_reference.js`.

**Ловушка округления.** `Math.round(14.5) === 15` в JS, `round(14.5) == 14`
в Python. В `m3_map` для этого есть `_js_round`. Не заменять на `round`.

### Расчёт Метода 3

**Ячейку матрицы задаёт число Ян в триграмме, и только оно.**
`CELL_BY_YANG = {0: "low", 1: "low", 2: "mid", 3: "high"}`. Координата внутри
ячейки на выбор ячейки не влияет, подвижность линий — тем более.

**Ось конкурентоспособности развёрнута к канону GE/McKinsey: сильная слева.**
`COL_INDEX = {"high": 0, "mid": 1, "low": 2}`, `X_SIGN = -1`.

**Подпись ячейки называет обе величины целиком** — формулировка утверждена
владельцем, собирается в `m3_verdict.cell_label`.

**Три дельты — разные величины:** `delta_portfolio`, `delta_direction`,
`delta_line`. У каждой полное имя, потому что их путают.

### Продуктовые решения

- Тип шага чек-листа `decision` не вводить.
- Повторной диагностики через 90 дней у Метода 3 нет.
- Название компании вводится перед диагностикой, из профиля не берётся.
- Надстрочная метка веб-отчёта Метода 1 намеренно отличается от PDF —
  владелец решил оставить как есть.

## 7. Чего в этом проекте лучше не делать

Список составлен по ошибкам, которые уже были допущены.

**Не ставьте разрушающую команду в один блок с проверкой,** результат которой
должен решать, выполнять ли её.

**Не считайте непустой JSON заполненными данными.** `{"focus": "", ...}` —
объект есть, значений нет. Проверка «отличается ли от текущего» на таком
объекте даёт ложную тревогу: `is distinct from` истинно и для пустых строк.

**Не заявляйте расхождение репозитория и прода, не проверив дважды.** Дважды
такое утверждалось и оба раза оказалось несохранённой работой.

**Не читайте `app.routes` для проверки маршрутов** — там ленивые обёртки
`_IncludedRouter` без `.path`. Правильная проверка: `app.openapi()["paths"]`.

**Не называйте числа по памяти.** Количество тестов, размеры файлов, номера
строк — измеряйте перед тем, как писать.

**Не считайте образец отчёта истиной.** В нём найдено фактическое противоречие
по линии 3.

**Не подгоняйте тест под реализацию.** Проверьте, дефект это или фикстура,
прежде чем менять код.

**Не доверяйте фикстуре карты как проверке парности.** Она сверяет расчёт с
эталоном при одинаковых входных данных и не видит расхождения, возникшего из
разных типов ключей у двух реальных вызовов.

```bash

echo "код: $?"; tail -3 /tmp/p.log

# миграции применены
docker compose exec -T backend python -m alembic current

# в git не уехало лишнее
git status --porcelain --ignored | grep -E '^\?\?|^!!' | grep -iE '\.env|secret'

# после интенсивной сессии сборок — снять кэш
docker builder prune -f && df -h /
```

**Проверка, что база поднимается с нуля** (не трогает боевую):

```bash
docker compose exec -T db sh -lc 'createdb -U "$POSTGRES_USER" dao64_chain_check'
docker compose exec -T -e DB_NAME=dao64_chain_check backend python -m alembic upgrade head
docker compose exec -T db sh -lc 'pg_dump -U "$POSTGRES_USER" -s "$POSTGRES_DB"' > /tmp/prod.sql
docker compose exec -T db sh -lc 'pg_dump -U "$POSTGRES_USER" -s dao64_chain_check' > /tmp/fresh.sql
docker compose exec -T db sh -lc 'dropdb -U "$POSTGRES_USER" dao64_chain_check'
```

Ожидаемые различия: позиция колонки `method`, отсутствие дефолта у
`strategies.id` на проде, расширения `pg_trgm`/`pgcrypto`/`uuid-ossp`
(наследие, ни одно не используется) и GRANT'ы. Всё остальное должно совпасть.

## 9. Одно замечание о методе

Отчёт называет позицию направления в матрице и говорит, что с ней делать.
Формулировки категоричны по форме — «Инвестировать точечно», «Пересборка
или выход». Это следствие того, что расчёт даёт одно число, а не распределение.

Расчёт опирается на отраслевые веса, помеченные в коде прямо: экспертные
априорные оценки, не эмпирические. Дисклеймер об этом печатается в каждом
отчёте, и убирать его не следует, даже если он портит вид страницы. Пока
отчётов не накоплено достаточно для пересмотра весов, уверенность в конкретной
цифре ниже, чем внушает её вид.

Это не повод смягчать формулировки — владелец выбрал прямой тон осознанно.
Это повод не добавлять новых утверждений сверх того, что даёт расчёт.
