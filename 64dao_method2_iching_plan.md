> (самооценка блоков BMC 0–5). План сохраняется для будущей реализации.
>
> Перед возвратом к нему разобрать замечание по калибровке: 2 утверждения на линию дают
> шаг среднего 0.5 против 0.25 у финблока, а пороги подвижности (>=3.5 / <=1.5) перенесены
> без пересчёта — доля подвижных линий будет завышена. Флаг `BORDERLINE_LINE` (2.40–2.60)
> при двух пунктах вырождается в единственное достижимое значение 2.50.

Текущее состояние: Метод 2 = самооценка 9 блоков BMC (балл 0–5 + комментарий, `method2_data` JSONB), без связи с И Цзин.
Зависимость: скоринг переиспользует обобщённые модули плана контуров (`contour_scoring`); реализуемо и до него — тогда обобщение делается здесь.

## 0. Зафиксированные решения

1. **Блок BMC → триграмма** через 3 линии зрелости (единая рамка для всех 9 блоков): линия 1 (нижняя) — *основа* (блок определён и подтверждён фактами, не гипотезами); линия 2 — *работоспособность* (функционирует системно и воспроизводимо); линия 3 (верхняя) — *развитие* (выдержит рост, адаптируется к изменениям).
2. **Ввод**: 6 утверждений на блок — по 2 на линию, ровно 1 реверсивное на блок; шкала 1–4 + «не знаю»; механика скоринга финблока (инверсия реверсивных, пороги 2.5 / 3.5 / 1.5, подвижные линии). Анкета = 54 утверждения + необязательный комментарий к каждому блоку. Вето-пункта нет (у блока BMC нет аналога приверженности первого лица).
3. **Пары блоков → гексаграммы отношений** (нижняя триграмма = внутренний блок, верхняя = внешний), v1 — 5 пар:

   | Пара | Нижняя (внутреннее) | Верхняя (внешнее) | Смысл |
   |---|---|---|---|
   | 1 | Ценностное предложение | Сегменты клиентов | Product-market fit |
   | 2 | Ключевые активности | Каналы | Доставка ценности |
   | 3 | Ключевые ресурсы | Ключевые партнёры | Устойчивость инфраструктуры |
   | 4 | Структура издержек | Потоки доходов | Юнит-экономика |
   | 5 | Ценностное предложение | Отношения с клиентами | Удержание клиентов |

4. **Интерпретация парных гексаграмм** — из существующей таблицы `strategies` (`title`, `fin_pattern_essence`, `fin_pattern_mistake`): заполненность всех 64 подтверждена проверкой БД 2026-07-20. Нового контента для пар не требуется.
5. **Комментарии сохраняются** (необязательные) — качественный слой отчёта и будущий вход AI-интерпретатора (2.2).
6. **Обратная совместимость**: legacy `method2_data` (v1: score 0–5 + text) продолжает читаться и рендериться по-старому; новые диагностики пишутся в формате v2.

## 1. Скоринг

### 1.1 Линия и триграмма блока

- Балл линии = среднее 2 пунктов (после инверсии реверсивного), 2 знака. Пороги финблока: ≥2.5 → A (Ян); ≥3.5 → старый Ян (подвижная); ≤1.5 → старый Инь (подвижная).
- Пропуски «не знаю»: 1 пропуск в паре пунктов → линия по одному пункту, флаг `PARTIAL_LINE`; 2 пропуска → линия не определяется, блок возвращается на дозаполнение. Лимит на анкету: ≤6 «не знаю» (пропорция финблока: 3 из 24 ≈ 6 из 54).
- Флаги качества: `INCONSISTENT_LINE` (разброс пары пунктов после инверсии ≥2), `BORDERLINE_LINE` (2.40–2.60), `STRAIGHTLINING` (≥45 из 54 сырых ответов одинаковы).
- Триграмма блока = код 3 линий снизу вверх (например `AAB`); одна из 8. Целевая триграмма = инверсия подвижных линий (строится при наличии хотя бы одной).

### 1.2 Гексаграммы пар

- Комбинация пары = линии 1–3 от нижнего (внутреннего) блока + линии 4–6 от верхнего (внешнего) блока → строка из 6 символов A/B → номер и название по `HEXAGRAM_LIST`.
- Целевая гексаграмма пары = целевые триграммы обоих блоков (при отсутствии подвижных линий в блоке — его текущая триграмма). Строится, только если хотя бы в одном блоке пары есть подвижные линии.
- Пример: Ценностное предложение = `AAB`, Сегменты = `BBA` → комбинация пары `AABBBA` → lookup в `HEXAGRAM_LIST` (контрольный кейс закрепить тестом с фактическим номером из таблицы).

## 2. Модель данных

Схема БД не меняется — `method2_data` остаётся JSONB, вводится версионирование payload:

```
method2_data (v2) = {
  "version": 2,
  "blocks": {
    "<block_key>": {
      "answers": {"1a": 3, "1b": null, "2a": 4, "2b": 2, "3a": 1, "3b": 3},
      "comment": "..." | null
    }, ...9 блоков
  },
  "result": {                                  # снимок, считает только сервер
    "blocks": {"<block_key>": {lines:[...], trigram, trigram_target, flags}},
    "pairs":  [{key, title, combination, number, name,
                combination_target?, number_target?, name_target?}],
    "quality_flags": [...]
  }
}
```

- `block_key` — латинские ключи: `value_proposition, segments, channels, relationships, resources, activities, partners, costs, revenues`; маппинг на русские названия — в конфиге. Legacy v1 использует русские label — при чтении определять формат по `version`.
- Снимок `result` обеспечивает воспроизводимость отчёта после правок контента (принцип финблока).

## 3. Backend

- `app/bmc_items.py` — конфиг 54 утверждений: `{item_id: '<block_key>.<line><a|b>', block_key, line (1–3), text, reverse}`. Инварианты (тест): 9 блоков × 6, по 2 на линию, ровно 1 реверсивное на блок.
- `app/bmc_scoring.py` — `compute_bmc_result(answers) -> result`. Расчёт линии переиспользует обобщённую функцию из `contour_scoring` (или обобщение выполняется в этом PR, если контуры ещё не реализованы). Триграммы, пары, флаги — по §1.
- `POST /api/assessments`: валидация v2 payload (полный набор item_id, значения ∈ {1..4, null}, лимит «не знаю»); сервер считает `result`; v1 payload больше не принимается на запись (400), но читается.
- `GET /api/method2/items` — блоки, утверждения, ярлыки шкалы (по образцу `method1/finance-items`).
- Контент: новый kind `bmc_block` в `fin_content` (9 записей — вводка/рамка блока; fallback на существующий `BMC_HELP` в коде). Характеристики триграмм — существующие 16 записей kind `trigram` (8 кодов × нижняя/верхняя позиция) переиспользуются для пар; для карты блоков — те же 8 характеристик без позиции (выбрать нижнюю как базовую или добавить 8 записей `trigram_block` — решить при реализации по фактическим текстам).

## 4. Отчёт (HTML + PDF синхронно)

Новая структура отчёта Метода 2 (заменяет сетку баллов для v2; v1 рендерится по-старому):

1. **Карта бизнес-модели**: 9 блоков в раскладке BMC, в каждом — SVG триграммы, название триграммы, балльный профиль 3 линий, подвижные линии выделены. Сильные/слабые блоки видны сразу.
2. **Гексаграммы отношений**: 5 карточек — SVG гексаграммы, номер, название (`strategies.title`), суть (`fin_pattern_essence`), типичная ошибка (`fin_pattern_mistake`); при наличии подвижных линий — целевая гексаграмма пары со своей сутью.
3. **Приоритеты**: подвижные линии по всем блокам, сортировка старый Инь → старый Ян, внутри — по блокам; каждая с расшифровкой линии (основа/работоспособность/развитие) в контексте блока.
4. **Комментарии владельца** по блокам (если заполнены).
5. **Оговорки по данным** (флаги качества).

SVG триграммы — половина существующего `_hexagram_svg` (вынести общий хелпер). `page-break-inside: avoid` на карточках.

## 5. Frontend

- Анкета Метода 2: степпер 9 блоков × 6 утверждений + поле комментария в конце блока; прогресс «Блок N/9»; переиспользовать компонент шкалы 1–4 финблока/`ContourSurvey`. Предупреждение об уходе со страницы.
- Отчёт: секции по §4.
- `lib/api.ts`: типы v2.

## 6. Тесты

1. Скоринг линии из 2 пунктов: инверсия реверсивного, пороги 2.5/3.5/1.5, `PARTIAL_LINE`, ошибка при 2 пропусках, лимит «не знаю».
2. Инварианты конфига 54 утверждений.
3. Сборка триграмм и парных гексаграмм — контрольный кейс с фиксированными ответами: ожидаемые 9 триграмм, 5 комбинаций, номера по `HEXAGRAM_LIST`; целевые пары при подвижных линиях.
4. Legacy: v1 payload читается и рендерится по-старому; v1 на запись → 400.
5. Фикстурный рендер PDF: v2 отчёт (все секции), v1 отчёт (регресс).
6. E2E: анкета v2 → generate-report → PDF содержит карту триграмм и 5 пар.

## 7. Порядок работ (этапы = отдельные PR)

1. `bmc_items.py` (тексты-заглушки) + `bmc_scoring.py` (+ обобщение расчёта линии, если контуры ещё не сделаны) + юнит-тесты.
2. API: валидация v2, снимок result, `GET /api/method2/items`; совместимость v1.
3. Рендер отчёта v2 (карта, пары, приоритеты) + фикстуры + регресс v1.
4. Фронт анкеты и отчёта.
5. Контент: 54 утверждения от владельца в конфиг; вводки блоков (kind `bmc_block`); проверка текстов триграмм.

## 8. Контент с владельца (критический путь)

- **54 утверждения** (9 блоков × 6): по 2 на линию «основа / работоспособность / развитие», 1 реверсивное на блок. Черновики готовит Claude, редактура — владелец.
- Вводки 9 блоков (можно стартовать с существующих `BMC_HELP`).
- Ревизия 16 текстов kind `trigram`: они писались для финблока — проверить универсальность формулировок для контекста BMC.

## 9. Риски

| Риск | Уровень | Митигация |
|---|---|---|
| 54 шага — длина анкеты | Средний | Степпер по блокам, draft-сохранение; Метод 2 — отдельный продукт, пользователь мотивирован |
| Тексты триграмм из финблока не лягут на BMC-контекст | Средний | Ревизия владельцем (п. 8); при необходимости — 8 записей `trigram_block` |
| Русские label в legacy v1 данных | Низкий | Version-детект при чтении, тест совместимости |
| ЦП участвует в двух парах — риск восприятия «двойного диагноза» | Низкий | Пояснение в отчёте: пары — разные проекции одного блока |

## 10. Вне скоупа

- Связь Метода 2 с контурами Метода 1 в сводной карте компании — после запуска обоих.
- AI-интерпретация комментариев и адаптация текстов — роадмап 2.2.
- Value Proposition Canvas как отдельная детализация пары PM-fit — кандидат в v2 Метода 2.
