## Этап H — хотфикс: отчёт Метода 1 с комбинацией `AAAAAA`

**Отдельно и первым.** Не зависит от расширения, чинит боевую ошибку. Деплоится и проверяется до всего остального.

### Причина

`AssessmentCreate.method2_data: dict[str, Method2Block] | None = None`, в роутере:

```python
method2_data={k: v.model_dump() for k, v in (body.method2_data or {}).items()}
```

При отсутствии данных Метода 2 в базу пишется `{}`, а не `NULL`. Детект в `build_report_html` рассчитан на `None`:

```python
is_method2 = method2_data is not None and (not combination or combination == 'AAAAAA')
```

`{} is not None` истинно → диагностика Метода 1 с комбинацией `AAAAAA` рендерится как Метод 2. Из отчёта выпадают раздел «01 Текущее состояние» и весь финансовый блок; секция BMC тоже не выводится, потому что `if method2_data:` для `{}` ложно.

### Решение

Детект метода переносится туда, где доступна вся запись, и опирается на содержательный признак, а не на `None` против `{}`. Схему БД не трогаем — это делает миграция 009.

**1. `backend/app/pdf.py`** — `build_report_html` получает необязательный параметр:

```python
def build_report_html(
    company_name: str,
    user_name: str,
    date_str: str,
    combination: str,
    strategy: Any | None,
    method2_data: dict[str, Any] | None,
    finance_result: dict | None = None,
    finance_interpretation: dict | None = None,
    finance_strategy: Any | None = None,
    lifecycle_stages=None,
    is_method2: bool | None = None,
) -> str:
```

Замена строки детекта:

```python
    if is_method2 is None:
        is_method2 = bool(method2_data) and (not combination or combination == 'AAAAAA')
```

Ключевое изменение: `method2_data is not None` → `bool(method2_data)`. Пустой словарь больше не считается признаком Метода 2. Явно переданный `is_method2` имеет приоритет.

**2. `backend/app/routers/assessments.py`** — в `build_html_for_assessment` перед вызовом:

```python
    is_method2 = bool(assessment.method2_data) or (
        not assessment.method1_answers and not assessment.method1_combination
    )
```

и передать `is_method2=is_method2` в `build_report_html`.

Второе слагаемое покрывает legacy-записи Метода 2 с пустой анкетой: если нет ни ответов Метода 1, ни комбинации — это Метод 2.

**Что НЕ делаем в хотфиксе:** не меняем запись `{}` на `None` в `create_assessment`. Это изменило бы значение `AssessmentOut.method2_data`, которое читает фронт, — лишний риск в срочной правке. Переходит в этап 1 вместе с колонкой `method`.

### Проверка на проде — до деплоя

```sql

       method1_combination,
```

## Этап 1 — миграция 009, модель, перенос финансовых данных

Самый рискованный этап. Деплой отдельно, полный регресс финансового флоу.

### Схема

**Таблица `assessment_contours`:**

```
id            UUID PK
assessment_id UUID FK assessments.id ON DELETE CASCADE, NOT NULL, index
contour       String(20) NOT NULL   CHECK IN ('finance','product','market','process')
answers       JSONB NOT NULL
result        JSONB NOT NULL
combination   String(6) NOT NULL    CHECK ~ '^[AB]{6}$'
created_at / updated_at
UNIQUE(assessment_id, contour)
```

**`assessments`:** новая колонка `method String(1) NOT NULL DEFAULT '1'` с `CHECK IN ('1','2')`. Заполнение по данным:

```sql
UPDATE assessments SET method = '2'
WHERE method2_data IS NOT NULL AND method2_data <> '{}'::jsonb;
```

Колонки `finance_*` **не удалять** — rollback-окно. Удаление отдельной миграцией 010 после стабилизации.

**`fin_content`:** колонка `contour String(20) NOT NULL DEFAULT 'common'`, `CHECK IN ('common','finance','product','market','process')`. Ограничение `uq_fin_content_kind_key` заменяется на `UNIQUE(kind, key, contour)`.

Sentinel `'common'` вместо `NULL` обязателен: в PostgreSQL `NULL` не конфликтует сам с собой в уникальном ограничении, две записи `(kind, key, NULL)` вставились бы обе и сломали резолюцию контента.

### Миграция данных

```sql
INSERT INTO assessment_contours (id, assessment_id, contour, answers, result, combination, created_at, updated_at)
SELECT gen_random_uuid(), id, 'finance', finance_answers, finance_result, finance_combination, created_at, updated_at
FROM assessments
WHERE finance_result IS NOT NULL AND finance_combination IS NOT NULL;
```

Сверка счётчиков до и после — обязательна, в отчёте по этапу.

Черновики (`finance_answers` без `finance_result`) остаются в старых колонках, завершатся в новую таблицу через обновлённый сабмит.

### Код

- Модели `AssessmentContour`, поле `Assessment.method`, поле `FinContent.contour`.
- `create_assessment`: писать `method2_data=None` вместо `{}`, проставлять `method`. Детект `is_method2` в `build_html_for_assessment` переводится на `assessment.method` (хотфикс H становится избыточным, но остаётся как страховка для legacy).
- Чтение финансового контура переключается на `assessment_contours`.
- `AssessmentOut`: поле `method`, список пройденных контуров.

### Тесты

Фикстура с финансовыми данными → перенос без потерь; отчёт до и после миграции идентичен; `downgrade` возвращает схему; регресс `test_finance_*` и `test_assessments.py`.

## Этап 5 — отчёт: секции контуров и сводная карта

### Целевая структура

```
Обложка
01 Текущее состояние       — базовая гексаграмма ЖЦ, ответы, параметры стратагемы
02 Целевой сценарий        — перенесён вверх (решения №10, №11)
03 Финансовая функция      — 8 подразделов + профиль стратегии + график ЖЦ
04 Сводная карта контуров  — при ≥2 пройденных контурах (решение №12)
05 Продукт/Сервис          ─┐
06 Операционные процессы    ├ только 8 подразделов интерпретации
07 Рынок и продажи         ─┘
```

При одном пройденном контуре разделы 04–07 отсутствуют целиком — дыр в нумерации не возникает.

### Обобщение рендера

`finance_section_html` → `contour_section_html`. Дешевле, чем предполагал план: полный профиль стратегии уже передаётся отдельным параметром `description_html` и вставляется между «Диагнозом» и «Профилем линий». Решение №9 реализуется передачей пустой строки для новых контуров.

Добавить параметры: набор блоков (сейчас `_FIN_BLOCKS` импортируется на уровне модуля), название контура, номер раздела. Сейчас `02` и «финансовая функция» захардкожены в заголовке и колонтитуле.

Попутно в зоне касания: подразделов фактически восемь, а не девять — план считал вместе с шапкой-гексаграммой; параметр `num` в локальной `h2(num, text)` не используется; в `build_report_html` мёртвый блок `page2` под `if False:` и неиспользуемая переменная `lifecycle_badge_html`.

### Сводная карта

Таблица: контур · текущая гексаграмма (SVG, номер, название) · результирующая · индекс зрелости · число подвижных линий. Контур-ограничение выделен.

**Выбор ограничения** — минимальный `maturity_index`. Формула индекса не меняется (решение №1), линия 5 остаётся в расчёте. Тай-брейки (решение №6): больше подвижных линий — раньше; затем фиксированный порядок finance → product → process → market. При полном равенстве ограничение не назначается, выводится формулировка «контуры сопоставимы по зрелости; выбор фокуса — управленческое решение».

Разрыв по индексу ≥3 между ограничением и следующим контуром — акцент: «рекомендуется сфокусировать ресурсы на этапе 1, остальные контуры в поддерживающем режиме».

### Разведение слоёв

Базовая гексаграмма ЖЦ и контурные берут номера из одного `HEXAGRAM_LIST`, но линии означают разное: типологический параметр против уровня зрелости. Обязательная оговорка в начале раздела 04 и визуальное различие карточек. Подвижные линии окрашиваются акцентом только в контурных гексаграммах — механизм уже есть в `_finance_hexagram_svg`.

### Критерий приёмки: паритет HTML и PDF

**Решение владельца 2026-07-21.** Обе версии отчёта несут одинаковую информацию, различается только форма подачи. Отчёт не обязательно скачивать, чтобы прочитать целиком.

Практически это значит: каждый раздел добавляется одновременно в `finance_pdf.py` и в `report/[id]/page.tsx`, пустые состояния выводятся с пояснением в обеих версиях, а не прячутся.

Правило появилось не на пустом месте. На этапе 2 сверка вскрыла три разъезда: в HTML отсутствовал раздел «Плановые шаги» в PDF, в HTML прятались пустые разделы, а траектория контура в браузере строилась по карте `_TARGET_HEXAGRAM` — то есть к финансовой гексаграмме применялся переход, предназначенный для базовой пары ЖЦ (прямое нарушение §0.1). При четырёх контурах и сводной карте разделов станет вчетверо больше, и такие расхождения будут накапливаться незаметно.

### Тесты

Отчёт с 1, 2 и 4 контурами · сводная карта появляется с ≥2 · legacy без контуров · вето отдельным блоком · фикстурный рендер полного 4-контурного отчёта с оценкой объёма (решение по свёртке принимать по факту) · `page-break-inside: avoid` на карточках · сверка состава разделов HTML против PDF.
