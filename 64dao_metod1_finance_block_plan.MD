# План реализации: финансовый блок в Методе 1 (64dao)

Исполнитель: Claude Sonnet/Opus в репозитории `Dmitry-pixel/64dao`.
Методологическая основа: `docs/finance_hexagram_questionnaire_spec.md` (спецификация опросника — приложить в репозиторий вместе с этим планом; далее — «Спецификация»). Разделы Спецификации: §2 — 24 пункта анкеты, §3 — правила скоринга, §5 — логика интерпретации (5 слоёв), §5.8 — эталонный отчёт, Приложение А — таблица кодов.

---

## 0. Зафиксированные решения

1. Финансовый блок (6 блоков × 4 подвопроса) — **расширение Метода 1**, не отдельная диагностика. Одна запись `assessments`, один кредит, одна генерация отчёта — структура кредитов и платежей не меняется.
2. Поток Метода 1: 6 базовых вопросов (как сейчас) → **обязательный** финансовый блок → сабмит одной диагностики. Пропуск блока не предусмотрен: на его основе строятся текущая и переходная финансовые гексаграммы отчёта. Итого анкета Метода 1 = 30 шагов (6 + 24).
3. Отчёт — **единый PDF с 4 гексаграммами**: (1) стадия ЖЦ по 6 базовым вопросам, (2) её целевое состояние по карте `_TARGET_HEXAGRAM`, (3) текущая финансовая гексаграмма, (4) переходная финансовая (инверсия подвижных линий). Существующие разделы (стадия ЖЦ, переход, таблица стратагемы — уже реализованы в `build_report_html`) + новый раздел «Финансовая функция» с 5 слоями.
4. 6 базовых вопросов **не изменяются и не разворачиваются** в подвопросы. Обоснование: это типологические дихотомии (B2B/B2C, централизованно/распределённо, последователь/первопроходец) — факты о типе бизнеса, а не шкалы зрелости. Усреднение шкал по ним семантически некорректно и обесценит существующий контент 64 стратегий, привязанный к бинарным комбинациям. Шкальная механика применяется только в финансовом блоке, где линия = оценка зрелости.
5. Контент интерпретации — **в БД, редактируется через админку** (по образцу `strategies`). Структура анкеты (24 пункта, реверсивность, вето) — конфиг в коде: это логика скоринга, а не контент.
6. Описания гексаграмм финансового раздела берутся из существующей таблицы `strategies` (title + новые поля паттерна). Контент заполнен для № 1–42; для остальных — существующий паттерн заглушки «Не заполнено».

## 1. Четыре гексаграммы в одном отчёте — не смешивать пары

| Аспект | Базовая часть (6 вопросов) | Финансовый блок (24 пункта) |
|---|---|---|
| Результат | Пара 1: стадия ЖЦ (`method1_combination`) + её целевое состояние | Пара 2: текущая + переходная гексаграммы фин. функции |
| Ответ | Бинарный A/B | Шкала 1–4 + «не знаю» |
| Линия | = один ответ | = среднее блока из 4 пунктов (после инверсии реверсивных) |
| Состояния линии | 2 (A/B) | 4 (старый/молодой Ян/Инь), подвижность при ≥3.5 / ≤1.5 |
| Целевая гексаграмма | Статичная карта `_TARGET_HEXAGRAM` | **Вычисляется**: инверсия подвижных линий (Спецификация §3.4). Карту `_TARGET_HEXAGRAM` НЕ использовать |
| Разделы отчёта | ЖЦ, переход, стратагема (как сейчас) | 5 слоёв (Спецификация §5) |

Это две независимые пары-проекции: комбинации между парами могут не совпадать, и это нормально — в отчёте пары не сравниваются и не смешиваются. Карта `_TARGET_HEXAGRAM` применяется только к паре 1, инверсия подвижных линий — только к паре 2.

## 2. БД — миграция 007

### 2.1 Расширение `strategies` (слой C — паттерны гексаграмм)

```
fin_pattern_essence  Text  — суть ситуации (1–2 предложения)
fin_pattern_mistake  Text  — типичная ошибка (1 предложение)
```

Используются и для текущей, и для результирующей гексаграммы (описание целевого состояния = `fin_pattern_essence` стратегии по результирующей комбинации).

### 2.2 Новая таблица `fin_content` (слои A, B, D, E)

Универсальная таблица контента — одна миграция и одна админ-страница:

```
id UUID PK
kind      String(20)  — 'tonality' | 'quadrant' | 'trigram' | 'tension_rule' | 'action_package'
key       String(40)  — уникален в рамках kind:
                        tonality: 'mature'|'transitional'|'crisis'
                        quadrant: 'scale'|'power_no_direction'|'ambition_no_engine'|'turnaround'
                        trigram:  'AAA_lower', 'AAA_upper', ... (8 кодов × 2 позиции = 16)
                        tension_rule: 'R1'..'R12'
                        action_package: 'line1_yin'..'line6_yin', 'line1_oldyang'..'line6_oldyang'
payload   JSONB       — {title?, text, condition?} ; для tension_rule condition хранится
                        справочно, исполняется код (см. 3.2)
sort      Integer
is_active Boolean default true
UNIQUE(kind, key)
```

### 2.3 Расширение `assessments`

```
finance_answers      JSONB       — {"1.1": 3, "1.2": null(=не знаю), ...} ; NULL допустим только
                                    для legacy-записей, созданных до релиза
finance_result       JSONB       — {lines:[{line,score,symbol,state,moving,flags}],
                                    combination_current, combination_resulting,
                                    moving_lines:[], maturity_index, quadrant,
                                    fired_rules:[], quality_flags:[]}
finance_combination  String(6)   — текущая фин. комбинация (для выборок/аналитики)
CHECK как у method1_combination (NULL допустим)
```

`finance_result` фиксируется сервером при создании completed-диагностики: отчёт воспроизводим даже после правки контента в админке.

## 3. Backend

### 3.1 `app/finance_items.py` — конфиг анкеты

24 пункта из Спецификации §2: `{item_id, block(1–6), block_title, text, reverse: bool, veto: bool}`. Реверсивные: 1.3, 2.3, 3.3, 4.4, 5.3, 6.3. Вето: 4.1. Отдаётся фронту через `GET /api/method1/finance-items` (или статикой во фронте — тогда синхронизировать тестом).

### 3.2 `app/finance_scoring.py` — скоринг (Спецификация §3, реализовать 1:1)

- Инверсия реверсивных: `5 − балл`.
- Балл линии = среднее блока, 2 знака. Пороги: ≥2.5 → A; подвижность ≥3.5 (старый Ян) / ≤1.5 (старый Инь). Граница 2.50 → Ян.
- Вето: `raw(4.1) == 1` → линия 4 = B (флаг `VETO_APPLIED`).
- Флаги: `INCONSISTENT_BLOCK` (разброс ≥2), `STRAIGHTLINING` (≥20 из 24 одинаковых), `BORDERLINE_LINE` (2.40–2.60), `PARTIAL_BLOCK` / ошибка при ≥2 пропусков в блоке, `VETO_UNKNOWN`.
- Комбинации: текущая — символы линий 1→6; результирующая — инверсия подвижных. Поиск номера — по `HEXAGRAM_LIST` из `app/hexagrams.py` (он уже совпадает с Приложением А Спецификации — проверено).
- Слои A/B: maturity_index = число A; квадрант — триграмма сильная при ≥2 Ян-линий; нижняя = линии 1–3, верхняя = 4–6.
- Правила напряжений R1–R12 — предикаты в коде (Спецификация §5.5), текст — из `fin_content`. Неактивное правило (`is_active=false`) не выводится.

### 3.3 API

- `POST /api/assessments` — расширить `AssessmentCreate`/`AssessmentOut` полем `finance_answers`. Для новой completed-диагностики Метода 1 поле **обязательно** (400 при отсутствии); draft допускается без него (частичное сохранение). Сервер сам считает скоринг (не доверять фронту) и пишет `finance_result` + `finance_combination`. Логика кредитов не меняется: это та же диагностика Метода 1.
- Валидация: полный набор из 24 item_id, значения ∈ {1,2,3,4,null}.
- `GET/PUT /api/fin-content` — CRUD для админки (по образцу `routers/strategies.py`, admin-only на запись).

### 3.4 PDF — расширение `build_report_html` в `app/pdf.py`

Новый раздел «Финансовая функция» добавляется после существующих блоков Метода 1. Для legacy-диагностик без `finance_result` (созданных до релиза) раздел не выводится — их отчёты должны регенерироваться без ошибок. Хелпер `_finance_section_html(...)`, структура — по эталону (Спецификация §5.8):

1. Заголовок раздела: гексаграмма текущая (номер, название из `hexagrams.py`, SVG через существующий `_hexagram_svg`; подвижные линии выделить цветом).
2. Диагноз: тональность (слой A) + `fin_pattern_essence` текущей.
3. Профиль 6 линий: балл, состояние, флаги (адаптация стилистики `_score_bar` под шкалу 1–4).
4. Квадрант + характеристики нижней/верхней триграмм (слой B).
5. Напряжения: сработавшие правила (слой D).
6. Приоритеты: подвижные линии (старый Инь раньше старого Яна) + пакеты действий (слой E).
7. Траектория: текущая → результирующая (SVG обеих; описание целевой = `fin_pattern_essence` + предостережение `fin_pattern_mistake` результирующей комбинации).
8. Оговорки по данным (флаги качества).
9. Следующие шаги: из пакетов действий подвижных линий (детерминированно, без LLM в v1).

Отсутствующий контент → заглушка «Не заполнено» (существующий паттерн). Если подвижных линий нет — блок траектории заменяется текстом «конфигурация стабильна». Раздел не должен ломать вёрстку при разрыве страниц (`page-break-inside: avoid` на карточках — по образцу существующих блоков).

## 4. Frontend

1. Поток Метода 1 в `assessment/page.tsx`: после 6-го вопроса — интерстициальный экран «Часть 2 из 2: финансовая функция, 24 утверждения, ~10 минут» с единственной кнопкой «Продолжить» (пропуска нет). Общий прогресс анкеты: `Шаг N/30` или `Часть 1–2`.
2. Финансовый блок: степпер 6 блоков × 4 утверждения; шкала 1–4 (ярлыки из Спецификации §1) + кнопка «Не знаю / нет данных»; заголовок и подсказка блока; прогресс `Блок N/6`. Переиспользовать стили вопросов Метода 1.
3. `submitMethod1()`: сабмит только после завершения обоих частей; `finance_answers` всегда в теле POST. Остальное (generate-report, waiting) — без изменений. Ответы обеих частей держать в состоянии страницы; при уходе со страницы предупреждать о потере данных (30 шагов — потеря болезненна).
4. `lib/api.ts`: типы finance-полей.
5. Дашборд/список диагностик: для диагностик с финансовым блоком — бейдж и две мини-гексаграммы (текущая/целевая).
6. Админка: страница «Финансовая интерпретация» — редактор `fin_content` по kind (по образцу `admin/strategies`) + два новых поля `fin_pattern_*` в существующем редакторе стратегии.

## 5. Тесты (обязательно)

1. Юнит скоринга — контрольный кейс Спецификации §3.7: сырые ответы → линии (3.25/3.25/3.00/3.25/1.75/1.00) → `AAAABB` (№ 34), подвижная линия 6, результирующая `AAAABA` (№ 14), флаг `INCONSISTENT_BLOCK` на блоке 3.
2. Границы: 2.50 → Ян; 3.50 → старый Ян; 1.50 → старый Инь.
3. Вето: 4.1=1 при среднем ≥2.5 → линия 4 = B + `VETO_APPLIED`.
4. Пропуски: 1 пропуск → среднее по 3 + `PARTIAL_BLOCK`; 2 пропуска → ошибка блока.
5. Реверсивные: инверсия применяется ровно к 1.3, 2.3, 3.3, 4.4, 5.3, 6.3.
6. Правила R1–R12: по кейсу на срабатывание/несрабатывание.
7. Сверка `HEXAGRAM_LIST` с эталонной генерацией из триграмм (порядок Вэнь-вана) — тест-константа.
8. Регресс и совместимость: новая completed-диагностика без `finance_answers` → 400; legacy-диагностика без `finance_result` → регенерация отчёта без фин. раздела, без ошибок; кредиты списываются как раньше (одна диагностика — один кредит).
9. E2E: POST анкеты с фин. блоком → generate-report → PDF содержит базовые разделы (ЖЦ, переход, стратагема) и все 9 подразделов фин. раздела.

## 6. Сопутствующее (малый скоуп)

- Контент `strategies` для № 43–64 отсутствует: отчёты по этим комбинациям (и базовая, и финансовая части) выходят с заглушками. Код менять не нужно — зафиксировать список пустых комбинаций запросом и отдать владельцу для заполнения через админку.
- Сиды: `backend/seed_fin_content.py` — стартовый контент из Спецификации §5 (3 тональности, 4 квадранта, 16 триграмм, 12 правил, пакеты действий; `fin_pattern_*` для № 34 и № 14 как образцы). Идемпотентно (upsert по kind+key), по образцу `seed_strategies.py`.

## 7. Порядок работ (этапы = отдельные PR)
