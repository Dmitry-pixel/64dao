# Спецификация и план: динамика стратегии и подписка (роадмап 3.1)

Исполнитель: Claude в репозитории `Dmitry-pixel/64dao`.
Зависимости: снимки `result` диагностик (Метод 1, контуры, Метод 2). Раздел «Динамика» строится на данных, которые уже сохраняются. Для приёма оплат подписки действует тот же блокер, что для всех платежей: production-готовность Точка Банк (verify_webhook, фискализация, refund).

---

## 0. Зафиксированные решения

1. **Подписка = разовый платёж за период доступа к разделу «Динамика»** по уже купленным отчётам пользователя. Не рекуррент: продление ручное (оплата нового периода как обычный заказ) + напоминания об окончании.
2. **Повторные диагностики докупаются разово** через существующий платёжный флоу. Модель оплаты отчётов не меняется; подписка — дополнительный продукт рядом, не вместо.
3. Подписка оформляется **на аккаунт пользователя** (покрывает все его компании). Основание: у большинства пользователей одна компания, схема проще; per-company вариант — возможное развитие для консультантов/HR (роадмап 4.3), структура данных это позволяет.
4. Период подписки и цена — настраиваются (период: конфиг, старт 12 месяцев; цена: через существующий `pricing_store`).
5. При активной подписке — **увеличенный лимит AI-чата** (параметр в настройках AI, связка с 2.2).
6. После окончания подписки раздел «Динамика» закрывается (замок + CTA продления), данные сохраняются полностью.

## 1. Сущности — миграция (следующий номер)

```
companies:     id, user_id FK, name String(255), created_at
               UNIQUE(user_id, name)
assessments:   + company_id UUID NULL FK companies.id
subscriptions: id, user_id FK, order_id FK NULL (NULL = выдана вручную админом),
               starts_at, ends_at, status ('active'|'expired'|'revoked'), created_at
orders:        + purpose String(20) DEFAULT 'report'  — 'report' | 'subscription'
```

- Активная подписка = запись со status='active' и `now() < ends_at` (статус 'expired' проставляется лениво при проверке).
- Миграция данных: создать `companies` из уникальных пар (user_id, company_name) завершённых диагностик, проставить `company_id`. Диагностики без company_name — компания «Без названия» (одна на пользователя).

## 2. Повторная диагностика

- В кабинете у компании — кнопка «Повторить диагностику»: создаёт новую диагностику с тем же `company_id`, прохождение и оплата — существующий флоу без изменений. Повторяются также контуры и Метод 2 (каждая диагностика — полный самостоятельный снимок).
- Ограничений частоты нет (пользователь платит за каждый прогон); напоминание о рекомендуемом квартальном ритме — §4.

## 3. Раздел «Динамика» (доступ при активной подписке)

Все вычисления детерминированы из снимков `result` — нового контента не требуется.

1. **Таймлайн компании**: все диагностики по датам, мини-гексаграммы, статусы.
2. **Базовая пара**: стадия ЖЦ тогда → сейчас; достигнута ли целевая гексаграмма предыдущей диагностики; смена стратагемы.
3. **Контуры**: график `maturity_index` по датам (по каждому контуру); таблица изменений линий (Инь→Ян / Ян→Инь по `line_key`); закрытые и новые подвижные линии; продвижение к результирующей гексаграмме предыдущего прогона; смена контура-ограничения.
4. **Метод 2**: изменение триграмм блоков и парных гексаграмм между прогонами.
5. **Сводка**: улучшилось / деградировало / без изменений — списками, с указанием линий и блоков.

Сравнение по умолчанию: последняя ↔ предыдущая; переключатель «с первой диагностикой». AI-комментарий динамики — v2 (на инфраструктуре 2.2, в `ai_context` добавляется блок динамики).

## 4. Напоминания (email, существующая инфраструктура)

- Подписчикам: за 14 дней до `ends_at` — о продлении; через N дней (конфиг, 90) после последней диагностики — «пора повторить диагностику, чтобы увидеть динамику».
- Без подписки: писем о динамике не шлём (не спамим; upsell — в интерфейсе отчёта).

## 5. Доступ и продажа

- Проверка активной подписки — единый helper (`subscription_service.is_active(user)`), используется API динамики и UI. Не дублировать проверку по роутерам (правило проекта).
- API: `GET /api/companies`, `GET /api/companies/{id}/dynamics` (403 без подписки), `POST /api/payments/create` с `purpose='subscription'`, admin CRUD подписок (ручная выдача/отзыв — работает до запуска платежей!).
- UI-апсейл: в отчёте при ≥2 диагностиках компании — превью-блок «Динамика» с замком и CTA; страница тарифа подписки.
- Feature flag `subscriptions_enabled` (runtime-конфиг по образцу `site_mode`, как в 2.2).

## 6. Frontend

- Страница «Мои компании» / карточка компании: таймлайн, кнопка повтора, вход в динамику.
- Страница «Динамика»: секции §3; графики — лёгкие SVG-спарклайны без тяжёлых библиотек (значений мало: точек = число диагностик).
- Профиль/кабинет: статус подписки, срок, кнопка продления.
- PDF динамики — вне скоупа v1 (онлайн-раздел only).

## 7. Правовая обвязка (до включения продаж подписки)

- Оферта: подписка как услуга периода (момент оказания, порядок продления, невозврат/возврат за неиспользованный период — согласовать со ст. 32 ЗоЗПП по образцу Section 10 текущей оферты).
- Фискализация чека для `purpose='subscription'`.

## 8. Тесты

1. Миграция companies: группировка по (user_id, company_name), диагностики без имени.
2. `subscription_service`: активна/истекла/отозвана, ленивый expire.
3. API динамики: 403 без подписки, корректные расчёты сравнения (фикстуры: 2 и 3 диагностики с известными изменениями линий), компания с 1 диагностикой (пустая динамика).
4. Повторная диагностика: company_id наследуется, оплата — регресс существующего флоу.
5. Админ-выдача подписки: доступ открывается без оплаты.
6. Регресс: отчёты и покупки без подписки не затронуты.

## 9. Порядок работ (этапы = отдельные PR)

1. Миграция (companies, company_id, subscriptions, orders.purpose) + `subscription_service` + админ-CRUD + тесты. После этого этапа подписку можно выдавать вручную — например, ранним клиентам.
2. Повторная диагностика (кнопка, наследование company_id) + регресс.
3. Расчёты динамики (чистый модуль сравнения снимков) + API + тесты.
4. Фронт: компании, динамика, апсейл-блоки.
5. Продажа подписки через Точка (`purpose='subscription'`) — **после** production-готовности платежей; до того подписка продаётся вручную (счёт → админ-выдача).
6. Email-напоминания.
7. Правовые документы → включение `subscriptions_enabled` для онлайн-продажи.

## 10. Риски

| Риск | Уровень | Митигация |
|---|---|---|
| Блокер платёжного контура (verify_webhook — заглушка) | Высокий (P0 для онлайн-продажи) | Этапы 1–4 и 6 не зависят от платежей; ручная выдача подписки админом — рабочая модель продаж до готовности Точки |
| Группировка legacy-диагностик по company_name (опечатки, разные написания) | Средний | Best-effort миграция + UI-инструмент «объединить компании» в кабинете (или админке) |
| Мало данных для динамики (1 диагностика) | Средний | Апсейл подписки показывать при ≥2 диагностиках; при 1 — CTA «повторите диагностику» |
| Возвраты за неиспользованный период подписки | Средний | Проработать в оферте до продаж (§7) |

## 11. Вне скоупа v1

- Рекуррентные списания (v2 — после проверки возможностей Точки).
- Per-company подписка и multi-seat (роадмап 4.3, консультанты/HR).
- AI-комментарий динамики, PDF-отчёт динамики.
- Чек-листы прогресса по шагам маршрута — роадмап 3.2 (строится на этой же структуре компаний).
